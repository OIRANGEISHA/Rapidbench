## Goal

Add an independently runnable SQLite Update benchmark to the existing Storage
module while preserving the behavior and result identifiers of the previously
published storage tests.

## Scope

- Add SQLite Update to the Database row in Insert, Update, Delete order.
- Keep all three Database cards equal in size and prevent long labels or
  five-digit results from overflowing.
- Prepopulate 100,000 rows outside the measured phase.
- Reuse one prepared Update statement inside 500-row immediate transactions.
- Update the timestamp, indexed value, text, and 512-byte payload for each
  selected row.
- Select rows from a deterministic shuffled sequence and cycle the sequence for
  the requested measurement duration.
- Verify every SQLite step and require exactly one changed row per Update.
- Extend the internal Storage result ABI from version 1 to version 2 so the
  native snapshot and Dart binding both contain 11 result slots.
- Preserve SQLite Insert as test ID 9 and SQLite Delete as test ID 10; assign
  SQLite Update ID 11 and move the internal All selector to ID 12.

## Compatibility and score interpretation

- CPU, GPU, memory, sequential storage, random storage, SQLite Insert, and
  SQLite Delete workloads are unchanged.
- Existing individual Storage results remain comparable with Beta 3 under the
  same device and test conditions.
- Bench All now includes one additional SQLite Update item and therefore takes
  longer to complete; RapidBench does not combine the database items into a
  single cross-version storage score.
- The Storage ABI change is internal to the APK. Native and Dart components are
  versioned and shipped together.
- SQLite throughput depends on filesystem state, cache behavior, firmware,
  thermal conditions, and background activity; it is not a theoretical UFS
  specification value.

- Reason: Earlier public Betas established the retained Android test
